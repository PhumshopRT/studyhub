9.3

RIS: การเชื่อมต่อและงานหลังบ้าน

report · tele-radiology · EMR · billing · เชื่อมซอฟต์แวร์ต่างผู้ผลิต
  • ออกรายงานได้หลายรูปแบบ (จำนวนตรวจ ปริมาณงานรายเครื่อง)
  • ส่งไปอ่านผลทางไกล (tele-radiology) ได้จาก RIS โดยตรง
  • เข้าถึง EMR แก้ไขข้อมูล และออกใบแจ้งหนี้ได้
  • เชื่อมต่อซอฟต์แวร์วินิจฉัยต่างผู้ผลิตให้ทำงานร่วมกัน
เคส CT brain เวรดึกที่ รพ.ชุมชน → กดส่งอ่านผลทางไกลจาก RIS → รังสีแพทย์ รพ.ศูนย์ส่งผลกลับใน 30 นาที → ผลเข้า RIS เดิม + ออกใบเรียกเก็บอัตโนมัติ

ข้อสังเกตสำคัญ

  • ข้อมูลผู้ป่วยพิมพ์ครั้งเดียว: HIS → RIS → modality worklist (ไม่ต้องคีย์ HN ซ้ำ ลดภาพสลับคน)
  • RIS ≠ PACS — RIS จัดการ "ข้อความ" · PACS จัดการ "ภาพ"
  • ผลอ่านจาก PACS ต้องวิ่งกลับ RIS ถึงจะปิดงานได้ ถ้าขาดจะเกิด "ภาพมีแต่ผลไม่มา"

9.4

Speech-to-Text / Digital Dictation

พูด → บันทึก → บีบอัด → ส่งเข้า RIS → ถอดความ → verify → เผยแพร่
  • แก้ไขไฟล์เสียงได้อิสระ — เดินหน้า ถอยหลัง แทรกเสียง (insert) เขียนทับ (overwrite)
  • เล่นย้อนฟัง (playback) ก่อนส่ง · บีบอัดได้หลายรูปแบบ
  • ส่งไฟล์เสียงเข้า RIS ได้โดยตรง · มี equalizer ปรับคุณภาพเสียง
ฟีเจอร์เหตุผล

9.5

Importing Examinations — นำเข้าการตรวจจากภายนอก

ดูตัวอย่างก่อนนำเข้า · จับคู่ผู้ป่วย · encapsulate · เก็บ Original Attributes
  • นำเข้าไฟล์ DICOM และไฟล์ภาพทั่วไปเข้าสู่คลัง PACS
  • จับคู่กับผู้ป่วยที่ถูกต้องใน RIS
  • ดูภาพตัวอย่างก่อนนำเข้า (ขยาย/ย่อ ปรับ contrast หมุนภาพ)
  • ภาพที่นำเข้าแล้วเรียกดูได้จาก EMR
"ดูตัวอย่างก่อนนำเข้า" ไม่ใช่ของฟุ่มเฟือย — แผ่น CD จากภายนอกมักมีหลายชุดภาพปนกัน บางแผ่นมีภาพผู้ป่วยคนอื่นติดมาด้วย
ปัญหาเกิดจากทางแก้
ข้อมูลผู้ป่วยไม่ตรงกันรพ.ต้นทางใช้ HN คนละระบบทำ DICOM tag mapping ให้ตรงกับ HN ปลายทาง
ภาพไปอยู่ผิดคนจับคู่ผิดตอนเลือกผู้ป่วยตรวจสอบชื่อ+วันเกิด+วันที่ตรวจก่อนยืนยัน
ไฟล์ไม่ใช่ DICOMJPEG/ภาพจากมือถือห่อเป็น DICOM (encapsulation) ก่อนจัดเก็บ
ข้อมูลเดิมหายเขียนทับ tag เดิมไม่เก็บสำเนาเก็บ Original Attributes ไว้เสมอ

ทำไมต้องเข้า PACS ไม่ใช่เก็บไฟล์ไว้เฉยๆ

  • เปิดเทียบภาพเก่า-ใหม่ในหน้าจอเดียว (สำคัญมากในเคสมะเร็ง)
  • สืบค้นได้ด้วย HN, วันที่, ชนิดการตรวจ
  • ควบคุมสิทธิ์เข้าถึง + log ตามกฎหมายคุ้มครองข้อมูล
  • ลดการตรวจซ้ำ — เชื่อมกับหลัก ALARA / justification
เครื่องมือปรับภาพ (zoom, contrast, rotate) ในหน้าตัวอย่าง แก้ไขไฟล์ต้นฉบับหรือไม่?
ไม่ใช่ — เป็นแค่การปรับการแสดงผลชั่วคราว ไฟล์ DICOM ต้นฉบับต้องไม่ถูกเปลี่ยน มิฉะนั้นใช้เป็นหลักฐานทางการแพทย์ไม่ได้ (ดู hash ในแบบจำลองจะไม่เปลี่ยน)

รายงานและสรุปผล (Reports and Summaries)

custom criteria · KPI · TAT · reject rate · PDPA

RIS ออกรายงานได้: การตรวจที่ทำไปแล้ว (แยกตามเครื่อง/ชนิด/ช่วงเวลา) · หน่วยงานที่ส่งตรวจ (OPD, IPD, ER, OR) · วัสดุที่ใช้ (สารทึบรังสี ฟิล์ม เข็ม สายน้ำเกลือ) · ต้นทุนของการตรวจ · custom criteria

ผู้ใช้รายงานที่ต้องการเอาไปทำอะไร
หัวหน้าแผนกปริมาณงานรายเครื่อง/รายเวรจัดอัตรากำลัง วางแผนซื้อเครื่อง
นักรังสีเทคนิคจำนวนภาพถ่ายซ้ำ (reject rate)ปรับเทคนิค ลดปริมาณรังสี
ฝ่ายการเงินต้นทุน–รายรับต่อการตรวจตั้งราคา เบิกจ่ายกองทุน
ฝ่ายพัสดุปริมาณสารทึบรังสีที่ใช้เติมสต็อกให้ทัน

KPI ที่ควรรู้จัก

  • TAT — เวลาจากถ่ายเสร็จถึงผลอ่านลงนาม
  • Reject/Repeat rate — เกณฑ์สากลมัก < 5–8%
  • Utilization rate · No-show rate · Cost per examination
reject rate เครื่อง CR ชี้ว่า chest PA ถ่ายซ้ำ 12% จากจัดท่าไม่ตรง → จัดอบรมทบทวน → เดือนถัดมาเหลือ 6% = ผู้ป่วยรับรังสีน้อยลง + ประหยัดเวลาเครื่อง
รายงานเหล่านี้ไม่ใช่การกรอกข้อมูลเพิ่ม แต่เป็นผลพลอยได้จากการบันทึกทุกขั้นตอน — ถ้าข้ามขั้นตอน รายงานเพี้ยนทันที (garbage in, garbage out) · ต้องระบุนิยาม "จำนวนการตรวจ" (ครั้ง/ท่า/ภาพ) · รายงานเชิงสถิติตาม PDPA ต้องปกปิดข้อมูลผู้ป่วย
ปีนี้ทำ CT เพิ่มขึ้น 30% เป็นข่าวดีหรือร้าย?
ยังบอกไม่ได้ ต้องดูควบคู่กับ appropriateness — ตัวเลขปริมาณอย่างเดียวไม่ใช่ตัวชี้วัดคุณภาพ

9.8

DICOM คืออะไร มาจากไหน

ACR + NEMA · โลกก่อนมี DICOM · เส้นเวลา 1983→1993

DICOM = Digital Imaging and Communications in Medicine เกิดจาก ACR (ฝั่งผู้ใช้งาน) และ NEMA (ฝั่งผู้ผลิต)

ถ้ามีแต่ผู้ผลิต มาตรฐานจะเอื้อธุรกิจ ถ้ามีแต่แพทย์ อาจสร้างสิ่งที่ผลิตจริงไม่ได้ — การจับมือกันคือเหตุผลที่ DICOM อยู่รอดถึงปัจจุบัน

โลกก่อนมี DICOM

  • ผู้ผลิตแต่ละรายใช้รูปแบบไฟล์ของตัวเอง (proprietary format)
  • ซื้อเครื่อง CT ยี่ห้อ A → ต้องซื้อจอยี่ห้อ A ตาม
  • เปลี่ยนยี่ห้อ = ข้อมูลเก่าเปิดไม่ได้ = vendor lock-in
เปรียบเหมือนปลั๊กไฟ — ถ้าแต่ละยี่ห้อมีหัวปลั๊กของตัวเอง บ้านหนึ่งหลังต้องมีเต้ารับสิบแบบ → DICOM คือ "หัวปลั๊กมาตรฐาน" ของวงการภาพทางการแพทย์
🎮 เส้นเวลา (คลิกแต่ละปี)timeline
จุดที่มักเข้าใจผิด: คิดว่ามี DICOM 4.0/5.0 — ความจริงเลขเวอร์ชันหยุดที่ 3.0 ตั้งแต่ปี 1993 แต่เนื้อหายังถูกเพิ่มทุกปี · จุดเปลี่ยนสำคัญที่สุดคือปี 1993 ที่ย้ายจากต่อสายตรง → สื่อสารผ่านเครือข่าย (TCP/IP) ซึ่งทำให้ PACS ปัจจุบันเกิดขึ้นได้

DICOM ไม่ใช่แค่ "นามสกุลไฟล์"

file format + network protocol ในมาตรฐานเดียว
ส่วนคืออะไรตัวอย่าง

องค์ประกอบของ Risk Scoring + เมทริกซ์ 5×5

Likelihood × Severity = Risk Score

1) โอกาสที่จะเกิด (Likelihood) 1–5

คะแนนระดับความหมาย
1Rareไม่น่าจะเกิดขึ้น — เกิดได้ยากมากหรือไม่เคยเกิดเลย
2Unlikelyไม่น่าเกิด — เกิดได้แต่ไม่บ่อยนัก
3Possibleอาจเกิดขึ้น — มีโอกาสเกิดบ้างเป็นครั้งคราว
4Likelyน่าจะเกิด — เกิดค่อนข้างบ่อย
5Certainเกิดขึ้นแน่นอน — เกิดบ่อยครั้งหรือคาดการณ์ได้ว่าจะเกิด

2) ความรุนแรงของผลกระทบ (Severity) 1–5

คะแนนระดับความหมาย
1Insignificantไม่มีความเสียหาย หรือเสียหายเล็กน้อยมาก
2Minorเสียหายเล็กน้อย แก้ไขง่าย ไม่กระทบผู้ป่วย/งานมากนัก
3Moderateเสียหายปานกลาง ต้องใช้เวลาแก้ไข กระทบผู้ป่วย/งานบ้าง
4Majorเสียหายรุนแรง ใช้ทรัพยากรมาก กระทบผู้ป่วยอย่างมีนัยสำคัญ หรือวินิจฉัยล่าช้า
5Catastrophicร้ายแรงถึงชีวิต พิการถาวร หรือหยุดชะงักการทำงานทั้งหมด

วิธีวิเคราะห์โจทย์: ให้คะแนน L และ S อย่างไร

กรอบคิด + หลักการ 6 ข้อที่อาจารย์มองหา

ให้คะแนน Likelihood ดูจาก

  • ข้อมูลย้อนหลัง: incident report / near-miss / reject rate
  • เครื่องป้องกันที่มีอยู่: interlock, checklist, worklist, barcode — ยิ่งมีมาก L ยิ่งต่ำ
  • Human factor: งานเร่งด่วน เวรดึก ความเหนื่อยล้า จำนวนเคสต่อวัน
  • สิ่งแวดล้อม: อุปกรณ์เก่า ไม่มี PM, พื้นที่แคบ/ลื่น, ผู้ป่วยกลุ่มพิเศษ

ให้คะแนน Severity ดูจาก 4 มิติ

  • ผู้ป่วย: เสียชีวิต/พิการถาวร (=5) · บาดเจ็บรุนแรง/วินิจฉัยล่าช้ามีนัยสำคัญ (=4) · ต้องรักษาเพิ่ม/เลื่อนนัด (=3) · เสียเวลาเล็กน้อย (=2) · แทบไม่มีผล (=1)
  • บุคลากร: รังสีสะสมเกินขีดจำกัด บาดเจ็บจากเข็ม/การเคลื่อนย้าย
  • องค์กร: คดีความ/PDPA/ชื่อเสียง/ค่าใช้จ่ายซ้ำ/หยุดบริการทั้งแผนก (=4–5)
  • คุณภาพงาน: ภาพใช้ไม่ได้ต้องถ่ายซ้ำ = ผู้ป่วยได้รังสีเพิ่ม (ALARA)

หลักการ 6 ข้อที่ต้องเขียนกำกับเสมอ

  • 2. คะแนนต่ำแต่ S = 4–5 ห้ามละเลย (เช่น เข็มซ้ำ 1×5=5, แพ้สารทึบรังสี 2×5=10) — "ความน่าจะเป็นต่ำแต่ผลยอมรับไม่ได้" ต้องมีมาตรการพร้อมเสมอ
  • 3. ทุกคะแนนต้องมีเหตุผลประกอบ — อาจารย์ให้คะแนนที่เหตุผล ไม่ใช่ตัวเลข
  • 4. หลังควบคุม ให้ประเมิน residual risk ซ้ำ ถ้ายัง High ต้องเพิ่มมาตรการหรือหยุดงาน
  • 5. Risk treatment: Avoid · Reduce · Transfer (ประกัน/สัญญา) · Accept + เฝ้าระวัง
  • 6. เชื่อมกับหลักวิชาชีพ: ALARA/justification, PDPA, patient safety goals
ทำไมเคส "ใช้เข็มซ้ำ" ได้แค่ 5 (Very Low) แต่ต้องเขียนว่า "ยอมรับไม่ได้"?
เพราะ Risk Score วัด "ความถี่ × ผล" แต่ไม่วัด "ความยอมรับได้ทางจริยธรรม/กฎหมาย" — เหตุการณ์ที่ผลคือเสียชีวิต+คดีอาญา แม้โอกาสต่ำมากก็ต้องควบคุม 100% (single-use, audit, near-miss reporting)

PACS คืออะไร + หลักการทำงานของระบบ

Picture Archiving and Communication System · Server + Storage + Image viewer/Workstation

PACS (Picture Archiving and Communication System) = ระบบสารสนเทศที่ทำหน้าที่จัดเก็บภาพที่ได้จากเครื่องถ่ายภาพ (Modality) ประเภทต่าง ๆ เข้าไว้ด้วยกันอย่างเป็นระบบ เพื่อให้สืบค้น เรียกดู และจัดเก็บภาพในระยะยาวได้อย่างมีประสิทธิภาพ

องค์ประกอบหน้าที่
Server (คอมพิวเตอร์แม่ข่าย) ประสิทธิภาพสูงจัดเก็บภาพไว้ในอุปกรณ์เก็บข้อมูล (Storage device)
Image viewer (โปรแกรมเรียกดูภาพ)ติดตั้งที่เครื่องลูกข่าย (Client) หรือ Workstation เพื่อเรียกดูภาพจากแม่ข่ายแพ็กส์

11.2

การทำงานร่วมกันของระบบสารสนเทศในงานรังสีวิทยา

HL7 · IHE · HIS ↔ RIS ↔ PACS ↔ Modality

การทำให้ระบบต่างกันแลกเปลี่ยนข้อมูลและทำงานร่วมกันได้ ต้องอาศัยมาตรฐานการเชื่อมต่อข้อมูล

  • HL7 (Health Level 7) — มาตรฐานกลางในการแลกเปลี่ยนข้อมูลระบบสารสนเทศทางการแพทย์ที่แตกต่างกันซึ่งติดตั้งในโรงพยาบาล (ตามสไลด์: พัฒนาจากความร่วมมือระหว่าง HIMSS และ RSNA)
  • IHE (Integrating the Healthcare Enterprises) — แนวทาง/กรอบความคิดในการเชื่อมต่อระบบ (ไม่ใช่มาตรฐานข้อมูลใหม่ แต่บอกว่านำ HL7 และ DICOM มาใช้เชื่อมระบบอย่างไร)
หมายเหตุเชิงวิชาการ: ในความเป็นจริง HL7 พัฒนาโดยองค์กร Health Level Seven International ส่วนความร่วมมือ HIMSS + RSNA คือที่มาของโครงการ IHE — เวลาสอบให้ยึดตามสไลด์ผู้สอน แต่ควรรู้ความต่างนี้ไว้

  • จัดเก็บภาพทั้งระยะสั้นและระยะยาว
  • รับและส่งภาพผ่านเครือข่ายคอมพิวเตอร์
  • นำภาพไปแสดง รวมถึงแบ่งปันภาพกับผู้ใช้ที่เรียกดูจากที่ต่าง ๆ ในองค์กร
  • รองรับการอนุญาตให้เข้าถึงข้อมูลจากผู้ใช้หลากหลาย ทั้งภายในและภายนอกโรงพยาบาล
  • อำนวยความสะดวกในกระบวนการวินิจฉัย ตั้งแต่เริ่มถ่ายภาพ → รับส่งภาพ → เก็บระยะยาวเพื่ออ้างอิงในอนาคต

ข้อดี/ข้อด้อยของระบบเดี่ยว (Standalone, Thick client)

ข้อดี
  • PACS หยุดทำงานแต่เครือข่ายปกติ → Modality/Workstation ยังมีข้อมูลส่งต่อไปได้ รังสีแพทย์ยังดูภาพและแปลผลได้ตามปกติ
  • เก็บข้อมูลและภาพหลายที่ → ลดความเสี่ยงสูญเสียข้อมูลภาพ
  • ข้อมูลตรวจย้อนหลังล่าสุดยังอยู่ที่ Workstation (มี short-term storage ในตัว)
  • ลดผลกระทบเมื่อเครือข่ายคับคั่ง — ภาพถูกส่งไป Workstation อัตโนมัติ เรียกดูได้ทันทีโดยไม่ผ่านเครือข่าย
  • ปรับ DICOM header ที่ QC Workstation ได้ทันทีก่อนส่งไปเก็บระยะยาว
ข้อด้อย
  • ต้องวางแผน Pre-fetching ล่วงหน้า → ไม่สะดวกถ้าต้องปรับขั้นตอนการทำงาน
  • ภาพใน short-term storage แต่ละ Workstation ต่างกัน → กระทบเมื่อรังสีแพทย์สลับเครื่อง
  • รังสีแพทย์อาจอ่านผลซ้ำเมื่อสลับเครื่อง
  • เพิ่ม Workstation ทุกครั้ง ต้องปรับปรุงกระบวนการวางแผนกระจายภาพระหว่าง PACS Server กับ Workstation ใหม่

ข้อดี/ข้อด้อยของระบบแม่ข่ายลูกข่าย (Client/Server, Thin client)

ข้อดี
  • ไม่ต้อง Pre-fetching เพื่อส่งไปยัง Workstation
  • ใช้งานสะดวก — ทุก Workstation เลือกรายการภาพได้ทุกรายการ
  • ลดการอ่านภาพซ้ำ เพราะรายการตรวจและภาพทั้งหมดอยู่ที่เดียว (PACS server)
ข้อด้อย
  • เก็บข้อมูลทั้งหมดที่เดียว → ถ้า PACS หยุดทำงาน เรียกดูภาพไม่ได้จากทุก Workstation จนกว่าระบบจะกลับมา
  • งานทั้งหมดอยู่ที่ PACS server → เสี่ยงมากกว่าระบบเดี่ยว
  • ขึ้นกับประสิทธิภาพเครือข่าย — ต้องรับส่งข้อมูลทุกครั้งที่เรียกดูภาพ
  • ปรับ DICOM header ที่ QC Workstation ไม่ได้ ต้องรอส่งไปเก็บระยะยาวที่ PACS Archive ก่อน แล้วจึงแก้ที่ PACS Server

การบริการรังสีวิทยาระยะไกล (Teleradiology)

2 รูปแบบ · Firewall · http (ไม่เข้ารหัส) vs https (เข้ารหัส)
รูปแบบลักษณะตามสไลด์
1) รูปแบบระบบแม่ข่ายลูกข่ายผู้ใช้ภายนอกเชื่อมกับ PACS ผ่าน Firewall และอินเทอร์เน็ต/Cloud โดยสารถูกเข้ารหัส (สัญลักษณ์กุญแจ+ซองจดหมาย) ไปยังเครื่องคอมพิวเตอร์ระยะไกล
2) แม่ข่ายลูกข่าย + อาศัยเว็บมี Web server และ Firewall ที่ขอบเครือข่าย ผู้ใช้ภายนอกเปิดผ่านเบราว์เซอร์ด้วย http (ไม่เข้ารหัส ซองเปิด) หรือ https (เข้ารหัส มีกุญแจ)
ข้อมูลผู้ป่วยส่งออกนอกโรงพยาบาลต้องผ่าน Firewall และควรใช้ https/การเข้ารหัส — ไม่ควรใช้ http ธรรมดา (Firewall คือด่านป้องกันระหว่างเครือข่ายภายในกับภายนอก)
🎮 แบบจำลอง: ส่งภาพออกนอกโรงพยาบาล + จำลองถูกดักจับข้อมูลhttp vs https
https = TLS เข้ารหัสทั้งข้อมูลผู้ป่วยและภาพ · http = เห็นเป็นข้อความดิบ ทั้ง HN ชื่อ วันเกิด และลิงก์ภาพ — ผิดทั้ง PDPA และมาตรฐานความปลอดภัย (โยง DICOM Part 15)

Enterprise Data Center · Long-term · Disaster recovery site · Redundant ห่าง 50–160 กม.
  • ศูนย์ข้อมูลระดับองค์กร (Enterprise Data Center) ให้การสนับสนุนการดำเนินการ PACS ในทุกระบบย่อย
  • ภาพผู้ป่วยทั้งหมดและข้อมูลผลการวินิจฉัยที่เกี่ยวข้องจาก PACS ทุกระบบ ถูกส่งไปเก็บระยะยาว (Long-term) ที่ศูนย์ข้อมูลระดับองค์กร
  • ศูนย์ข้อมูลระดับองค์กรจัดการความเสี่ยงจากภัยพิบัติที่อาจกระทบข้อมูลภาพและอุปกรณ์

คำศัพท์: Acquisition gateway = ตัวกลางรับภาพจาก Modality เข้าสู่ระบบ · QC Workstation = เครื่องตรวจสอบคุณภาพภาพ/ข้อมูลก่อนส่งเข้า Archive (แก้ DICOM header ได้) · Redundant = ซ้ำซ้อนมีสำรอง · DR = การกู้คืนระบบเมื่อเกิดภัยพิบัติ

ควรบริหารจัดการเพื่อลดค่าใช้จ่าย โดยอาจถ่ายโอนข้อมูลจาก short-term ไป long-term ใน 3–5 ปี หรือส่งไปทันที (ขึ้นกับนโยบาย) · องค์กรเลือกติดตั้งระบบเอง หรือใช้บริการผู้ให้บริการที่มีแผนกู้คืนภัยพิบัติชัดเจน

การบีบอัดข้อมูลภาพ (Image compression) และการเก็บระยะยาว

ข้อแนะนำการใช้ Lossy compression มาจากแนวทางของราชวิทยาลัยรังสีแพทย์แห่งสหราชอาณาจักร ร่วมกับ European Society of Radiology — แนะนำให้ใช้ได้เพื่อลดค่าใช้จ่าย เช่น ภาพเอกซเรย์ทรวงอกบีบอัดได้ 10:1 โดยไม่สูญเสียรายละเอียดที่จำเป็นทางคลินิกเมื่อเทียบกับต้นฉบับ

กฎสำคัญ: Lossy compression ทำเพื่อการเก็บระยะยาว (Long-term) เท่านั้น — Short-term ไม่ควรบีบอัด · Lossy = สูญเสียข้อมูลบางส่วน กู้ต้นฉบับกลับ 100% ไม่ได้ · Lossless = ไม่สูญเสีย

VNA (Vendor Neutral Archive)

หัวใจ 3 คำ · PACS vs VNA · ทำไมมี DICOM แล้วยังไม่พอ · exit strategy

VNA = เทคโนโลยีจัดเก็บภาพทางการแพทย์ ที่เก็บภาพและเอกสาร (รวมถึงไฟล์ใดก็ตามที่เกี่ยวข้องทางคลินิก) ไว้ในรูปแบบมาตรฐาน ผ่านส่วนต่อประสานมาตรฐาน เพื่อให้ระบบอื่นเข้าถึงได้โดยไม่ผูกติดกับผู้ผลิตรายใด

หัวใจ 3 คำ: Vendor Neutral Standard format + interface Archive (คลังระยะยาว)

แก้ปัญหา vendor lock-in — VNA คือคำตอบระดับระบบทั้งโรงพยาบาล ต่อปัญหาเดียวกับที่ DICOM แก้ในระดับไฟล์

ทำไมมี DICOM แล้วยังไม่พอ

  • DICOM เป็นมาตรฐานกลาง แต่ผู้ผลิตเลือกทำเฉพาะบางส่วน
  • PACS แต่ละยี่ห้อมักเก็บข้อมูลบางอย่างในรูปแบบของตัวเอง (private tags, โครงสร้างฐานข้อมูลภายใน)
  • เปลี่ยนยี่ห้อ PACS ทีหนึ่ง = ต้องย้ายข้อมูลทั้งคลัง (data migration) ซึ่งใช้เวลาเป็นปีและค่าใช้จ่ายสูงมาก
โรงพยาบาลใช้ PACS ยี่ห้อ A มา 12 ปี สะสมภาพหลายร้อยล้านภาพ พอจะเปลี่ยนไปยี่ห้อ B พบว่าต้องจ้างย้ายข้อมูลด้วยงบประมาณสูงกว่าค่า PACS ใหม่เสียอีก → จึงจำใจต่อสัญญากับยี่ห้อเดิม
นี่คือแรงจูงใจที่แท้จริงของ VNA — ไม่ใช่เรื่องเทคนิคล้วน ๆ แต่เป็นเรื่องอำนาจต่อรองและความเป็นเจ้าของข้อมูล โรงพยาบาลต้องการเป็นเจ้าของข้อมูลตัวเอง ไม่ใช่ให้ข้อมูลเป็นตัวประกันของผู้ขาย

Cheat Sheet บทที่ 11

หน้าเดียวก่อนสอบ

พื้นฐาน + เชื่อมต่อ

  • PACS = Server (เก็บภาพลง storage) + Image viewer ที่ Client/Workstation
  • HL7 = ข้อความ (HIS↔RIS↔PACS) · DICOM = ภาพ (PACS↔Modality) · IHE = กรอบวิธีเชื่อม
  • เกณฑ์ PACS ใหญ่: ใช้จริงทุกวัน · Modality ≥ 4–5 · ≥ 20,000 exams/ปี · เครือข่าย+DICOM
  • วิวัฒนาการ: 1972 สแกนฟิล์มใน ICU · 1983 DoD สนับสนุน teleradiology · 1980–1990 PACS ใหญ่ · UW + Georgetown + Philips + AT&T

DICOM header

  • 128 ไบต์ preamble + "DICM" + elements
  • pixel = frames × rows × cols × (bits/8) × SPP → 2×109×91 = 19,838 ไบต์ · header 794 → รวม 20,632 ≈ 20.6 KB
  • 0002 File Meta · 0008 Identifying · 0010 Patient · 0018 Acquisition · 0028 Image Presentation
  • Transfer Syntax 1.2.840.10008.1.2.1 = Explicit VR Little Endian (ไม่บีบอัด)

สถาปัตยกรรม

  • Standalone/Thick = มี short-term ที่เครื่อง, auto-distribute + pre-fetch, PACS ล่มยังอ่านได้, แก้ header ที่ QC ได้, แต่สลับเครื่องเสี่ยงอ่านซ้ำ
  • Client-Server/Thin = เก็บที่ server ที่เดียว, ลบภาพหลังอ่าน, ไม่ต้อง pre-fetch, ลดอ่านซ้ำ, แต่ล่ม=จบ, พึ่งเครือข่าย, แก้ header ที่ QC ไม่ได้
  • Web-based = ใช้ browser, เหมาะ teleradiology, ฟังก์ชันจำกัด/ช้ากว่า
  • Enterprise PACS = Enterprise Data Center + DR site ห่าง 50–160 กม.

Storage / บริการ

  • Short-term ≥ 3–5 ปี, แสดงภาพ ≤ 3 วิ, DR กู้ ≤ 1 ชม. · Long-term = อ้างอิง ราคาประหยัด · ห้ามใช้ long-term เป็น DR ของ short-term
  • Lossy 10:1 (CXR) ทำได้เฉพาะ long-term · short-term ห้ามบีบอัด
  • บริการ: 24/7, one-stop, วิศวกร on-site + remote, รองรับ third party, online issue tracking, DR ระบุในสัญญา
  • Transfer delay = เข้า PACS − ถ่าย · Reporting delay = แปลผล − เข้า PACS · TAT = แปลผล − ถ่าย

VNA

  • Vendor Neutral + Standard format/interface + Archive · เก็บทั้ง DICOM และ non-DICOM (PDF/JPEG/วิดีโอ/ECG/pathology)
  • แก้ vendor lock-in ระดับโรงพยาบาล · Tag morphing, Universal viewer, XDS/DICOMweb, Lifecycle management
  • พิสูจน์ความเป็นกลาง = exit strategy (export มาตรฐาน → import ยี่ห้ออื่นได้)
